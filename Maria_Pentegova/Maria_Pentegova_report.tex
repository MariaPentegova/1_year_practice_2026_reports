\section{Введение}

Обход графа в ширину (BFS, Breadth-First Search) является базовым алгоритмом обработки графов. Он используется для поиска кратчайших путей в невзвешенных графах, анализа связности и как составная часть более сложных алгоритмов. Время работы BFS зависит не только от числа вершин и рёбер, но и от структуры графа: распределения степеней вершин, диаметра и того, какая часть графа достижима из исходной вершины.

BFS можно реализовать двумя принципиально разными способами. Классический подход хранит граф в виде списков смежности, например в формате CSR (Compressed Sparse Row), и обрабатывает вершины по одной с помощью очереди. Линейно-алгебраический подход представляет граф разреженной матрицей смежности и выражает один шаг обхода через умножение разреженного вектора на эту матрицу. Такой подход реализован в стандарте GraphBLAS и его реализации SuiteSparse:GraphBLAS.

Преимущество линейно-алгебраического подхода не гарантировано на графах любого вида: каждая операция над разреженными структурами имеет накладные расходы, которые окупаются только при достаточном объёме работы на одном шаге обхода. Поэтому выбор подхода требует экспериментального исследования на графах разной топологии.

\section{Постановка задачи}

\textbf{Целью работы является} экспериментальное сравнение производительности классического последовательного обхода графа в ширину на базе формата CSR и линейно-алгебраического обхода на базе SuiteSparse:GraphBLAS на графах различной топологии и определение того, на каких графах предпочтителен каждый из подходов.

Для достижения поставленной цели были решены следующие задачи:
\begin{itemize}
    \item реализовать классический BFS на CSR-представлении графа;
    \item реализовать BFS на GraphBLAS с представлением графа в виде разреженной матрицы смежности;
    \item обеспечить обработку ориентированных и неориентированных графов без изменения исходной ориентации рёбер;
    \item проверить корректность классической реализации с помощью независимой реализации из Boost Graph Library (BGL);
    \item измерить время работы обеих реализаций на семи графах различной топологии;
    \item по результатам измерений определить, для каких графов выгоднее GraphBLAS, а для каких~--- классический подход.
\end{itemize}

Основным объектом сравнения являются две реализации: классический BFS на CSR и BFS на GraphBLAS. BGL используется только как контрольная реализация и в основное сравнение не входит.

\section{Реализация классического и линейно-алгебраического BFS}

Решение реализовано на языке C (стандарт C11); программа замеров написана на C++17, так как вызывает шаблонную библиотеку BGL. Сборка выполняется с помощью CMake.

\textbf{Представление графа.} Графы загружаются из файлов формата Matrix Market (\texttt{.mtx}) без весов рёбер. Исходная ориентация сохраняется: для ориентированного графа (\texttt{general}) ребро $u \to v$ добавляется только в одну сторону, для неориентированного (\texttt{symmetric})~--- в обе. Это необходимо, потому что в ориентированном графе направление рёбер определяет множество достижимых вершин, и его изменение исказило бы исследуемую топологию. Граф хранится в формате CSR: массив \texttt{row\_ptr} длины $n+1$ задаёт границы списка соседей каждой вершины, массив \texttt{col\_idx} содержит номера соседей подряд. Соседи в каждой строке сортируются, повторяющиеся рёбра удаляются. Отсортированная CSR-структура без повторов передаётся в GraphBLAS функцией \texttt{GxB\_Matrix\_import\_CSR}, поэтому обе реализации обходят один и тот же граф, представленный одинаковыми массивами.

\textbf{Классический BFS.} Вершины извлекаются из очереди по одной, просматриваются их исходящие рёбра в CSR, ещё не посещённые соседи получают предка и добавляются в очередь. Время работы~--- \mbox{$O(|V| + |E|)$}, дополнительная память~--- $O(|V|)$. Реализация однопоточная.

\textbf{BFS на GraphBLAS.} Граф хранится как булева разреженная матрица смежности $A$, в которой элемент $A(i,j)$ присутствует, если есть ребро $i \to j$. Состояние обхода задаётся двумя разреженными векторами: \texttt{frontier}~--- текущий фронт, \texttt{parent}~--- предки уже посещённых вершин. Пока фронт не пуст, повторяются две операции:
\[
\texttt{frontier}\langle\neg\texttt{parent}\rangle = \texttt{frontier} \cdot A, \qquad
\texttt{parent}\langle\texttt{frontier}\rangle = \texttt{frontier}.
\]
Умножение вектора на матрицу (\texttt{GrB\_vxm}) выполняется в полукольце \texttt{ANY.SECONDI}: операция \texttt{SECONDI} записывает в найденную вершину $j$ номер вершины фронта $k$, из которой есть ребро $k \to j$, то есть предка, а \texttt{ANY} выбирает любого из возможных предков. Дополнение маски \texttt{parent} отбрасывает уже посещённые вершины. Маска структурная: учитывается наличие элемента, а не его значение, иначе вершина с предком~$0$ считалась бы непосещённой. GraphBLAS работает в неблокирующем режиме и может откладывать вычисления, поэтому в конце обхода вызывается \texttt{GrB\_Vector\_wait}, и весь обход гарантированно попадает в измеряемое время. Операции GraphBLAS выполняются параллельно средствами OpenMP.

Обе реализации выполняют один и тот же алгоритм~--- обход по уровням в направлении исходящих рёбер (top-down). Обход с переключением направления (direction-optimizing BFS) не используется ни в одной из них, так как это другой алгоритм, а в работе сравниваются подходы при одинаковой постановке задачи.

\textbf{Режимы обхода.} Каждая реализация поддерживает два режима: обход из одной вершины (single-source) и обход одновременно из нескольких вершин (multisource), в котором для каждой вершины находится путь до ближайшего из источников. Второй режим позволяет проверить, как меняется соотношение подходов, когда обход начинается с нескольких фронтов. В GraphBLAS он отличается от первого только начальным вектором, в классической реализации~--- начальным содержимым очереди.

\textbf{Результат обхода и проверка корректности.} Обе реализации возвращают дерево предков \texttt{parent}: для источника $\texttt{parent}[s] = s$, для остальных достижимых вершин~--- вершина, из которой она была впервые достигнута, для недостижимых~--- $-1$. Дерево предков, в отличие от одних расстояний, позволяет восстановить сами кратчайшие пути. Предок вершины в BFS определён неоднозначно: вершину может открыть любой её сосед с предыдущего уровня. Поэтому результаты разных реализаций сравниваются не поэлементно, а с помощью функции \texttt{bfs\_tree\_depths}. Она вычисляет глубину каждой вершины в дереве и проверяет, что в цепочках предков нет циклов, что каждое ребро дерева $\texttt{parent}[v] \to v$ существует в графе и что для каждого ребра $u \to v$ из посещённой вершины вершина $v$ тоже посещена и $\mathrm{depth}[v] \le \mathrm{depth}[u] + 1$. Из этих условий следует, что глубины равны кратчайшим расстояниям от источников. Два результата считаются совпадающими, если оба дерева корректны и глубины всех вершин равны. Проверка выполняется за \mbox{$O(|V| + |E|)$}.

\textbf{Контрольная реализация BGL.} Чтобы сравнение с GraphBLAS было осмысленным, классическая реализация должна быть корректной и не должна быть искусственно медленной. Для проверки обоих условий используется функция \texttt{breadth\_first\_search} из Boost Graph Library~--- независимая реализация того же алгоритма. BGL не включается в основное сравнение: цель работы состоит в сравнении двух вычислительных подходов, а не нескольких библиотек, и дополнительные реализации со своими внутренними особенностями затруднили бы выделение влияния топологии графа. По той же причине не используется библиотека LAGraph: её BFS содержит эвристики, в частности переключение направления обхода, и сравнение с ней смешало бы влияние подхода и влияние этих эвристик.

\textbf{Тестирование.} Корректность проверяется автоматическими тестами, запускаемыми через CTest. Тесты используют неориентированный граф из пяти вершин и ориентированный граф из четырёх вершин, в котором одна вершина недостижима из остальных; ожидаемые расстояния посчитаны вручную. Тест \texttt{test\_load} проверяет загрузку файлов Matrix Market, построение CSR для ориентированных и неориентированных графов и отклонение некорректных файлов. Тест \texttt{test\_check} проверяет, что функция \texttt{bfs\_tree\_depths} обнаруживает несуществующее ребро, цикл, пропущенную вершину и не кратчайший путь. Тест \texttt{test\_bfs} запускает обе реализации из каждой вершины обоих графов, в режиме multisource, а также с некорректными аргументами. Тест \texttt{test\_comparison} напрямую сравнивает результаты классической реализации и GraphBLAS.

\textbf{Методика.} Для обхода из одной вершины выбиралась вершина с максимальной исходящей степенью, чтобы обход не завершался сразу из-за того, что из стартовой вершины почти ничего не достижимо. Для ориентированных графов степень считалась по исходящим рёбрам, то есть по тем, по которым идёт обход. Для режима multisource выбирались четыре различные вершины с ненулевой исходящей степенью, равномерно случайно, генератором с фиксированным начальным значением: такой выбор не подстраивается под структуру графа, исключает изолированные источники и воспроизводится при каждом запуске. Построение CSR, матрицы GraphBLAS и графа BGL выполнялось один раз до замеров и в измеряемое время не входило, так как одно и то же представление графа используется для многих обходов. В замер входил только сам обход и получение результата в собственном формате реализации: для классической реализации~--- заполнение массива \texttt{parent}, включая его начальную инициализацию значением $-1$, для GraphBLAS~--- создание векторов, обход и завершение отложенных операций. Перевод вектора GraphBLAS в массив нужен только для проверки результата и выполнялся вне замера. Каждая реализация запускалась один раз для прогрева, а затем 10~раз с измерением времени функцией \texttt{clock\_gettime} с часами \texttt{CLOCK\_MONOTONIC}. Для каждой серии вычислялись среднее, минимальное и максимальное время. После замеров результаты всех реализаций сравнивались функцией \texttt{bfs\_tree\_depths}.

Ускорение GraphBLAS относительно классической реализации вычислялось по формуле
\[
S = \frac{T_{\mathrm{CSR}}}{T_{\mathrm{GB}}},
\]
где $T_{\mathrm{CSR}}$ и $T_{\mathrm{GB}}$~--- среднее время классического BFS и BFS на GraphBLAS соответственно. Значение $S > 1$ означает, что быстрее GraphBLAS, $S < 1$~--- что быстрее классическая реализация.

\textbf{Характеристики обхода.} Чтобы связывать время работы с топологией графа по измеренным величинам, а не по предположениям, для каждого обхода вычислялись характеристики, не зависящие от реализации: доля достигнутых вершин, число уровней (максимальная глубина плюс один), размер наибольшего уровня и число просмотренных рёбер~$M$, равное сумме исходящих степеней достигнутых вершин. Именно эти рёбра просматривает обход по уровням в любой из двух реализаций. Из них получаются две производные величины: \emph{число рёбер на уровень}~--- отношение $M$ к числу уровней, характеризующее объём работы на одном шаге обхода, и \emph{MTEPS}~--- миллионы просмотренных рёбер в секунду, $M/T$, мера скорости BFS, построенная по аналогии с TEPS из рейтинга Graph500 и позволяющая сравнивать графы разного размера. Характеристики вычисляются по проверенному дереву классической реализации после всех замеров и на измеряемое время не влияют.

\textbf{Стенд.} Эксперименты проводились на процессоре Intel Core Ultra~7 255H (16~ядер, 16~потоков) с 32~ГБ оперативной памяти под управлением Ubuntu~26.04.1~LTS. Использовались компилятор GCC~15.2.0, SuiteSparse:GraphBLAS~7.4.0 и Boost~1.90.0. Сборка выполнялась в конфигурации \texttt{Release} с флагами \texttt{-O3 -DNDEBUG}. Классическая реализация и BGL работали в одном потоке, GraphBLAS~--- в 16~потоках. Возможность параллельно выполнять операции над разреженными матрицами является одним из основных свойств линейно-алгебраического подхода, поэтому подходы сравниваются в том виде, в котором они применяются на практике.

\textbf{Анализ результатов.} Таблица~\ref{tab:traversal} показывает, что выбор подхода определяется объёмом работы на одном уровне обхода. Графы разделяются на две группы, между которыми нет пересечений ни в одном из режимов.
\begin{itemize}
    \item На всех графах, где на уровень приходится не более $1{,}3 \cdot 10^5$ рёбер, классическая реализация быстрее в обоих режимах ($S$ от 0,12 до 0,91). Сюда входят дорожные сети, граф цитирования, граф взаимодействия и веб-граф.
    \item На обеих социальных сетях, где на уровень приходится от $4{,}5 \cdot 10^6$ до $3{,}3 \cdot 10^7$ рёбер, быстрее GraphBLAS: в 3,03--4,22~раза при обходе из одной вершины и в 3,51--4,67~раза при обходе из четырёх.
\end{itemize}

Скорость классической реализации меняется от графа к графу относительно слабо (от 24,9 до 136,3~MTEPS), а скорость GraphBLAS~--- более чем на два порядка (от 3,4 до 417,2~MTEPS). Это согласуется с устройством линейно-алгебраического обхода: каждый уровень выполняется как одна операция над разреженными структурами, и её накладные расходы, в том числе на распределение работы между 16~потоками, окупаются только при большом числе рёбер на уровне. На \texttt{com-Orkut} обход занимает 7~уровней по $3{,}3 \cdot 10^7$ рёбер, и GraphBLAS обрабатывает 413~млн рёбер в секунду против 136~млн у классической реализации. На \texttt{road\_usa} обход занимает 6\,809~уровней примерно по $8{,}5 \cdot 10^3$ рёбер, и GraphBLAS обрабатывает 11,7~млн рёбер в секунду против 59,6~млн.

Число рёбер на уровень становится известно только после обхода. Из характеристик, известных заранее, с ним согласуется средняя степень вершин (таблица~\ref{tab:graphs}): GraphBLAS выигрывает только на двух графах со средней степенью 14,2 и 76,3, а на всех пяти графах со средней степенью от 2,4 до 5,6 проигрывает.Для графов с промежуточной средней степенью в исследованном наборе данных представителей нет, поэтому определение точной границы перехода между областями эффективности подходов выходит за рамки настоящей работы.

Ориентация рёбер сама по себе выбор подхода не определяет: среди ориентированных графов GraphBLAS выигрывает на \texttt{soc-LiveJournal1} и проигрывает на \texttt{web-Google} и \texttt{cit-Patents}, среди неориентированных выигрывает на \texttt{com-Orkut} и проигрывает на остальных. Ориентация влияет на результат через множество достижимых вершин, что видно на графе \texttt{cit-Patents}. Ссылки в нём ведут только на ранее выданные патенты, и даже из вершины с максимальной исходящей степенью достижимо лишь 3,4\% вершин, а из четырёх случайных источников~--- 1,2\%. На этом графе GraphBLAS проигрывает сильнее всего ($S = 0{,}12$ и~$0{,}15$) и показывает наименьшую скорость, 3,4~MTEPS. Обход из одной вершины занимает у него 4,4~мс на уровень, тогда как на дорожных сетях, где размер уровней того же порядка,~--- от 0,36 до 0,72~мс, хотя в \texttt{road\_usa} вершин в шесть раз больше. Следовательно, когда из источника достижима малая часть большого графа, затраты GraphBLAS не уменьшаются пропорционально объёму обхода. Такая ситуация характерна для ориентированных графов ссылок и зависимостей.

На \texttt{web-Google} при обходе из одной вершины разница наименьшая ($S = 0{,}91$), но диапазоны времени двух реализаций пересекаются (52,6--89,9 и 76,1--95,3~мс), поэтому на этом графе в данном режиме значимого различия нет. При обходе из четырёх источников классическая реализация быстрее и здесь: её наибольшее время меньше наименьшего времени GraphBLAS.

Обход из нескольких источников не изменил вывода ни для одного графа: каждый граф остался в той же группе, что и при обходе из одной вершины.

\textbf{Ограничения.} Полученные выводы относятся к исследованному набору графов и стенду. Для каждого графа измерялись обход из одной стартовой вершины и из одного набора из четырёх источников. Классическая реализация однопоточная, а GraphBLAS использует 16~потоков, поэтому ускорение $S$ отражает совокупный эффект линейно-алгебраического подхода и его параллельного выполнения; число потоков GraphBLAS можно ограничить переменной окружения \texttt{OMP\_NUM\_THREADS}, если требуется разделить эти эффекты.

\section{Заключение}

В ходе работы получены следующие результаты:
\begin{itemize}
    \item реализованы классический BFS на CSR и BFS на SuiteSparse:GraphBLAS, каждый в режимах обхода из одной вершины и из нескольких вершин; обе реализации возвращают дерево предков и обрабатывают ориентированные и неориентированные графы без изменения ориентации рёбер;
    \item реализована проверка корректности результата BFS, не зависящая от выбора предков, и написаны автоматические тесты загрузки графов, проверки результата и обеих реализаций;
    \item корректность классической реализации подтверждена сравнением с независимой реализацией из BGL на всех семи графах;
    \item измерено время работы обеих реализаций на семи графах различной топологии и для каждого обхода вычислены характеристики, связывающие время работы со структурой графа; результаты GraphBLAS совпали с результатами классической реализации на всех графах.
\end{itemize}

На основе измерений можно сформулировать следующие рекомендации по выбору подхода:
\begin{itemize}
    \item для графов с большой средней степенью и малым числом уровней обхода, таких как социальные сети \texttt{com-Orkut} и \texttt{soc-LiveJournal1} (средняя степень 14,2 и 76,3, от $4{,}5 \cdot 10^6$ рёбер на уровень), следует выбирать GraphBLAS: он быстрее в 3,03--4,67~раза;
    \item для графов с малой средней степенью (2,4--5,6 в исследованном наборе) и не более $1{,}3 \cdot 10^5$ рёбер на уровень следует выбирать классический BFS на CSR; для дорожных сетей с сотнями и тысячами уровней обхода он быстрее в 3,6--6,5~раза;
    \item для ориентированных графов, в которых из источника достижима лишь малая часть вершин, классический BFS также предпочтителен: на \texttt{cit-Patents} он быстрее в 6,5--8,4~раза.
\end{itemize}

Дальнейшее уточнение областей применимости требует расширения набора тестовых графов структурами с промежуточными характеристиками плотности.
