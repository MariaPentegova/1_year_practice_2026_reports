\section{Введение}

Граф~--- это математическая структура, состоящая из вершин (узлов) и рёбер (связей между ними). Граф называется связным, если между любой парой его вершин существует путь по рёбрам (все вершины образуют единую компоненту). Если граф у графа есть изолированные компоненты, он называется несвязным. Граф называется неориентированным, если связь между вершинами двусторонняя. Граф называется ориентированным, если связь имеет строгое направление. Граф называется плотным, если число рёбер (\(E\)) близко к максимально возможному числу рёбер в графе, иначе~--- разреженными.

\textbf{Граф можно хранить в памяти несколькими способами:}

\begin{itemize}
    \item \textbf{Матрица смежности.} Представляет собой таблицу размера $|V| \times |V|$ (где $|V|$~--- число вершин). Если между двумя вершинами есть ребро, в соответствующей ячейке ставится~1, иначе~--- 0.
    \item \textbf{Матрица инцидентности.} Таблица размера $|V| \times |E|$ (где $|E|$~--- число рёбер). Каждый столбец соответствует одному ребру и содержит две единицы в строках тех вершин, которые это ребро соединяет.
    \item \textbf{CSR (\texttt{Compressed Sparse Row}).} Сжатое хранение разреженных матриц. Это самый эффективный способ для алгоритмов анализа графов (таких как BFS). Граф хранится в виде двух массивов: значение по индексу вершины в первом массиве указывает на индекс начала её соседей в другом массиве. Последний элемент первого массива указывает на длину второго массива, тем самым определяя его границу. В данной работе графы представлены в виде матриц формата CSR.
\end{itemize}

Алгоритм BFS (\texttt{Breadth-First Search})~--- это алгоритм анализа графов, реализующий обход в ширину. Обход начинается с одной вершины (источника), которая помечается как уровень~0 (фронт). На следующем шаге находятся все непосещённые соседи источника, образующие уровень~1. Затем находятся непосещённые соседи вершин первого уровня, образующие уровень~2, и так далее. Таким образом, каждый шаг обхода формирует новый уровень вершин.

\textbf{Ключевые метрики BFS:}

\begin{itemize}
    \item \textbf{Максимальный уровень} (\texttt{max\_level}): количество шагов от источника с максимальной степенью до самой удалённой достижимой вершины.
    \item \textbf{Средняя ширина фронта} (\texttt{avg\_width}): отношение количества вершин к максимальному уровню ($|V| / \text{max\_level}$).
    \item \textbf{Максимальная ширина фронта} (\texttt{max\_width}): максимальное количество вершин на одном уровне. Такая метрика позволяет понять стоимость каждого шага операции BFS.
    \item \textbf{Средняя степень вершины}: отношение количества рёбер к количеству вершин ($|E| / |V|$). Такая метрика позволяет оценить плотность графа.
\end{itemize}

При обработке больших графов (социальные сети, маршрутизация, анализ связей) ИТ-компании часто сталкиваются с выбором инструмента для обхода в ширину. Использование библиотеки GraphBLAS и параллельных вычислений требует значительных ресурсов процессора. Если задача решается на специфичном графе (например, на сильно разреженной дорожной сети) или в ней не требуется узнавать многие глобальные свойства графа (например, полную матрицу расстояний для каждой вершины), компании тратят вычислительные ресурсы и деньги впустую, выбирая GraphBLAS вместо классического подхода.

\section{Постановка цели исследования}

\textbf{Цель работы} заключается в том, чтобы на основе замеров скорости определить, в каких случаях накладные расходы на матричные операции GraphBLAS окупаются (то есть параллельная нагрузка на процессор оправдана), а когда не окупаются и целесообразно выбирать классический подход.

Для достижения поставленной цели были выполнены \textbf{следующие задачи:}

\begin{itemize}
    \item реализовать классический BFS и GraphBLAS BFS с построением дерева предков на языке~C;
    \item найти универсальные метрики графа, которые позволят однозначно определить границу между подходами;
    \item разработать консольную утилиту, которая автоматически анализирует граф пользователя и выдаёт рекомендацию по выбору оптимального подхода;
    \item сравнить классическую реализацию по производительности с эталонной библиотекой BGL (\texttt{Boost Graph Library}), чтобы подтвердить эффективность собственного кода на~C;
    \item написать подсистему модульных тестов для проверки корректности обеих реализаций;
\end{itemize}

\section{Описание решения}

В работе детально сопоставляются два принципиально разных подхода:

\begin{itemize}
    \item \textbf{Классический BFS (итеративный подход).} В классической реализации обхода в ширину используется очередь~--- структура данных, работающая по принципу <<первым пришёл~--- первым вышел>> (FIFO).Шаг обхода выглядит следующим образом: вершина извлекается из головы очереди, при этом указатель head сдвигается на следующий элемент. Затем в CSR-структуре перебираются все её соседи. Для каждого непосещённого соседа его родителем записывается извлечённая вершина, после чего сосед добавляется в конец очереди (по указателю tail), а указатель tail сдвигается на следующую свободную позицию. Данный подход представляет собой строго последовательный алгоритм, выполняемый в одном потоке процессора.
    \item \textbf{GraphBLAS BFS (матричный подход).} GraphBLAS — это библиотека, которая позволяет работать с графами через операции линейной алгебры. В данном подходе вместо очереди используется вектор фронта. Шаг обхода выполняется через умножение вектора на матрицу с использованием инвертированной маски visited (список посещённых вершин). Маска исключает из результата вершины, которые уже были посещены на предыдущих уровнях. Для построения дерева предков (\texttt{parent}-BFS) используется специальное полукольцо \texttt{ANY\_FIRSTJ}. В нём стандартная арифметика заменяется на: операция «умножения» (\texttt{FIRSTJ}) извлекает \textbf{индекс вершины-предка}, из которой пришло ребро, а операция «сложения» (\texttt{ANY}) позволяет выбрать любого из возможных предков на предыдущем уровне. Полученные индексы сохраняются в массив \texttt{parent}. Затем с помощью функции \texttt{GrB\_apply} с операцией \texttt{GxB\_ONE\_BOOL} значения родителей конвертируются в логические единицы, формируя булев вектор нового фронта для следующей итерации. Выполнение всех этих матричных операций автоматически распределяется библиотекой по всем доступным ядрам процессора.
\end{itemize}

Для автоматизации выбора алгоритма требовалось найти универсальные числовые характеристики графа. В процессе исследования были рассмотрены три варианта метрик.

\textbf{Вариант 1: Отношение \texttt{avg\_width / max\_level}.} Эта метрика оказалась неподходящей, так как использование средней ширины приводило к сильному сглаживанию данных. При таком подходе пиковые нагрузки оказывались скрыты на отдельных шагах, где GraphBLAS работает гораздо быстрее классики. В итоге формировались неверные рекомендации для графов с большим количеством уровней, где большинство фронтов были узкими, но меньшинство~--- экстремально широкими (превышающими среднее значение в сотни раз).

\textbf{Вариант 2: Отношение \texttt{max\_width / max\_level}.} На маленьких графах данный показатель приводил к ложной корреляции: деление даже небольшой пиковой ширины на малое число уровней давало искусственно завышенные значения. На основе данной метрики ошибочно выдавалась рекомендация в пользу GraphBLAS для примитивных графов, где классический подход справлялся за доли миллисекунды. Кроме того, отношение не учитывало среднюю степень вершины ($|E|/|V|$), напрямую влияющую на скорость умножения разреженных матриц.

\textbf{Вариант 3: Максимальная ширина фронта (\texttt{max\_width}) + средняя степень вершины ($|E|/|V|$).} Эта комбинация показала себя наиболее стабильно. Средняя степень вершины характеризует разреженность графа, а максимальная ширина фронта характеризует пиковую вычислительную нагрузку. Вместе они полностью описывают, насколько эффективно распараллелится операция умножения вектора на матрицу в GraphBLAS.

\section{Экспериментальный стенд и анализ границ применимости}

Для обеспечения воспроизводимости и чистоты замеров эксперименты проводились на строго фиксированном стенде со следующими характеристиками:

\begin{itemize}
    \item \textbf{Процессор:} \texttt{Intel(R) Core(TM) Ultra 7 255H}. 16 физических ядер (Hyper-Threading отключен), базовая частота 2.0 ГГц, максимальная частота 5.1 ГГц, кэш L3 объемом 24 МБ.
    \item \textbf{Оперативная память:} 32 ГБ LPDDR5.
    \item \textbf{Операционная система:} Ubuntu 26.04.1 LTS (ядро Linux 7.0.0-38-generic).
    \item \textbf{Компилятор и сборка:} GCC 15.2.0 (флаг оптимизации \texttt{-O3}), CMake 4.2.3.
    \item \textbf{Библиотеки:} SuiteSparse:GraphBLAS 10.5.1, Boost 1.90 (BGL).
\end{itemize}

Исследование проводилось на выборке из \textbf{54 графов}, которые делятся на две категории:

\begin{itemize}
    \item \textbf{Реальные графы} из открытой коллекции University of Florida Sparse Matrix Collection (SuiteSparse), включая \texttt{com-Orkut}, \texttt{roadNet-CA}, \texttt{wiki-Talk}, \texttt{cit-Patents} и другие.
    \item \textbf{Синтетические графы}, специально сгенерированные на языке Python для поиска точных границ применимости (графы серий \texttt{probe\_*} и \texttt{wiki\_*} с контролируемой средней степенью вершины и шириной фронта).
\end{itemize}

Перед каждым запуском частота процессора жёстко фиксировалась на максимальном значении с помощью утилиты Performance Governor (\texttt{sudo cpupower frequency-set -g performance}), чтобы убрать разброс скоростей. Переменная окружения \texttt{OMP\_NUM\_THREADS} не задавалась, поэтому в GraphBLAS использовалось все 16 доступных потоков. Каждый замер времени выполнения (в микросекундах) усреднялся по 10 независимым запускам.

По результатам анализа экспериментальных данных все 54 графа были разделены на четыре зоны.

Классика выигрывает при выполнении хотя бы одного из следующих условий (пороги определены эмпирически на основе анализа пограничных графов):

\begin{itemize}
    \item \textbf{Средняя степень вершины $< 1.4$.} Граф слишком разрежен для параллельных вычислений.
    \texttt{probe\_n3000k\_d1.5\_hub} (степень 0.75, ширина 1.5~млн)~--- классика быстрее в 4.3 раза. Даже огромная ширина фронта не окупает накладные расходы GraphBLAS, если степень слишком мала.
   \texttt{probe\_n3000k\_d1.8} (степень 1.80, ширина 968~тыс.)~--- GraphBLAS быстрее в 1.4 раза. Переход через степень 1.4 при большой максимальной ширине делает матричный подход эффективнее.

    \item \textbf{Средняя степень вершины $< 4.4$ при ширине фронта $< 600~000$.}
    \texttt{probe\_n800k\_d4.0\_wide} (степень 4.0, ширина 434~тыс.)~--- классика быстрее. Несмотря на широкий фронт ($>290$ тыс.), степени 4.0 не хватает для окупаемости матричных операций.
    \texttt{probe\_n1200k\_d4.5\_wide} (степень 4.50, ширина 694~тыс.)~--- GraphBLAS быстрее в 1.88 раза. Пересечение порога в 4.4 и ширины в 290~тыс. меняет предпочтительный подход.

    \item \textbf{Средняя степень вершины $< 31.0$ при ширине фронта $< 290~000$.}
    \texttt{wiki\_sub560k\_density\_15} (степень 15.0, ширина 287~340)~--- классика быстрее в 2.5 раза. Ширина почти достигла 290 тыс., но степени все еще недостаточно для окупаемости матричных операций.
     \texttt{probe\_n500k\_d15.0\_srandom} (степень 15.0, ширина 424~934)~--- GraphBLAS быстрее в 3.0 раза. Даже при средней степени вершины $< 31.0$, но при ширине фронта, превысившей 290 тыс., использовать матричный подход становится предпочтительнее .

    \item \textbf{Средняя степень вершины $> 31.0$ при ширине фронта $< 60~000$.}
    \texttt{flickr\_abs\_60000\_density\_35} (степень 35.0, ширина 28~тыс.)~--- классика быстрее в 5.8 раза. При экстремально высокой степени, но малой ширине накладные расходы GraphBLAS всё ещё не окупаются.
    \texttt{flickr\_density\_35} (степень 35.0, ширина 83~тыс.)~--- GraphBLAS быстрее в 1.34 раза. Как только ширина превыщают 60 тыс., затраты на параллелизм окупаются.
\end{itemize}

\section{Результаты экспериментов}

Классический BFS демонстрирует более высокую скорость и предпочтителен в следующих случаях:

\begin{itemize}
    \item Средняя степень вершины $< 1.4$.
    \item Средняя степень вершины $< 4.4$ при ширине фронта $< 600~000$.
    \item Средняя степень вершины $< 31.0$ при ширине фронта $< 290~000$.
    \item Средняя степень вершины $> 31.0$, но ширина фронта $< 60~000$.
\end{itemize}

\textbf{Во всех остальных случаях} предпочтительнее библиотека GraphBLAS:

\begin{itemize}
    \item Средняя степень $> 31.0$ и ширина фронта $> 60~000$.
    \item Средняя степень $> 4.4$ и ширина фронта $> 290~000$.
    \item Средняя степень $> 1.4$ и ширина фронта $> 600~000$.
\end{itemize}

\section{Сравнение производительности с эталонной реализацией BGL}

Помимо проверки корректности, было проведено сравнение скорости работы разработанного классического BFS на чистом~C с эталонной реализацией \texttt{Boost Graph Library} (BGL).

На подавляющем большинстве протестированных графов (включая все реальные графы) классический код на C показал лучшее время (в 0.35--0.85 быстрее). Единственными исключениями стали сверхплотные синтетические графы probe\_n4000k\_d40.0 и probe\_n3000k\_d30.0 (средняя степень 40 и 30), где BGL оказался быстрее в 1.17 и 1.01 раза соответственно.

Замеры системного профилировщика perf (отношение метрик cache-misses к cache-references) на плотных графах демонстрируют долю промахов кэша последнего уровня (LLC) до 70\%, и производительность BFS становится ограничена пропускной способностью оперативной памяти (Memory Wall). В этих условиях шаблонная реализация BGL позволяет компилятору C++ сгенерировать более оптимальный код для работы с памятью (за счёт векторизации и предвыборки данных). Однако на реальных графах со сложной топологией эти микрооптимизации теряют эффективность, и классическая реализация на C стабильно обгоняет BGL.

\section{Проверка корректности}

\textbf{Структурная корректность (связные и несвязные графы).} На тестовых графах из 5 вершин (связный: 0-1, 1-2, 0-3, 1-4, 3-4, несвязный: 0-1, 2-3, изолированная 4) проверялось, что обе реализации (Classic и GraphBLAS) корректно обходят все достижимые вершины и вычисляют уровни, а недостижимые вершины остаются с уровнем~\texttt{-1}. Также проверялось, что источник указывает сам на себя, и для каждой вершины (не источника) её родитель является её соседом в графе, а сама вершина не образует петлю (не указывает на себя). Тесты запускались из \texttt{разных} стартовых вершин (0 и 1), чтобы исключить зависимость от выбора старта.

В графах с циклами до некоторых вершин можно добраться разными путями одинаковой длины, и в алгоритме BFS в качестве родителя может быть выбрана любая вершина предыдущего уровня, поэтому используется проверка вида \texttt{parent[v] == 1 || parent[v] == 3}, которая позволяет выбрать любого из родителей вершины.

\textbf{Тест сравнения с эталонной библиотекой BGL (Boost Graph Library).} Данный тест реализован на C++ и запускается на обоих исходных тестовых графах (связном и несвязном), где проверяется совпадение шагов трёх реализаций: классической на C, матричной на GraphBLAS и эталонной BGL. В ходе тестирования поэлементно сравниваются множества посещённых вершин и структуры предков, полученные каждой из реализаций. Поскольку BGL является признанной в индустрии библиотекой с открытым исходным кодом, полное совпадение результатов подтверждает не просто согласованность разработанных алгоритмов между собой, но и их строгую \textbf{математическую корректность} относительно мирового эталона.

Тесты запускались как по отдельности, так и в составе единого набора (через систему сборки \texttt{CTest}), и во всех сценариях демонстрировали 100\% успешное прохождение.

\section*{Заключение}

В ходе выполнения работы были получены \textbf{следующие результаты}, соответствующие поставленным задачам:

\begin{itemize}
    \item Реализованы классический и матричный алгоритмы обхода графа в ширину с построением дерева предков (\texttt{parent}-BFS) на языке C.

    \item Найдены универсальные метрики для определения границы применимости: средняя степень вершины (\(|E|/|V|\)) и максимальная ширина фронта (\texttt{max\_width}). На основе анализа 54 графов выведены эмпирические границы, позволяющие определить, когда GraphBLAS окупает накладные расходы, а когда выгоднее использовать классический подход.

    \item Разработана консольная утилита \texttt{bfs\_analysis}, которая анализирует структуру графа пользователя, вычисляет необходимые метрики и выдаёт обоснованную рекомендацию по выбору оптимального алгоритма.

    \item Проведено сравнение классической реализации на C с эталонной библиотекой BGL. На подавляющем большинстве реальных графов собственная реализация оказалась быстрее BGL. Исключение составили лишь сверхплотные синтетические графы, где BGL выиграл за счёт лучших микрооптимизаций компилятора C++.

    \item Написана подсистема модульных тестов (запускаемая через CTest), которая проверяет корректность обеих реализаций на связных и несвязных графах, а также сравнивает результаты с эталонной библиотекой BGL. Все тесты проходят успешно (100\%).
\end{itemize}
